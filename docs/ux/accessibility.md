# Accessibility requirements - first slice

Target: **WCAG 2.2 level AA** for every screen in `screens.md`, on current phone browsers (iOS Safari, Android Chrome) and laptop browsers. Builders cite these IDs in test names (e.g. `it("UX-006 links each error to its field")`); the UX review checks them one by one. Each requirement says how to test it: **[unit]** = Vitest + Testing Library in `apps/web`, **[axe]** = automated check (`@axe-core/playwright` or `vitest-axe`) on each screen state, **[manual]** = a person with keyboard / screen reader / zoom.

## General (customer and admin)

- **UX-001 Keyboard operable.** Every interactive element can be reached with Tab / Shift+Tab and operated with Enter or Space (radios and the frame choice with the arrow keys); there is no keyboard trap except inside an open modal dialog (UX-024); the Tab order follows the visual order top-to-bottom, left-to-right. Only native interactive elements (`button`, `a[href]`, `input`, `select`, `summary`) or elements with the matching ARIA role and key handling; no click handlers on `div`/`tr`. (2.1.1, 2.1.2, 2.4.3) **[unit]** each action fired via `userEvent.keyboard`; **[manual]** tab through each screen.
- **UX-002 Focus visible and not hidden.** Every focusable element shows the focus ring from the tokens (`:focus-visible`, 3 px `color.focus`, 2 px offset, at least 3:1 against the background, see `design-tokens.md`); `outline: none` is never used without this replacement; a focused element is never fully covered by the sticky admin header or any other content (`scroll-padding-top: header-height + space.4`). (2.4.7, 2.4.11, 1.4.11) **[manual]** tab through at 1280 px and 390 px; **[unit]** the CSS lint/grep in CI finds no `outline: none`/`outline: 0` outside `tokens.css`.
- **UX-003 Focus and title after navigation.** After every customer step change (C1->C2->C3->C4->C5->C6, and back) and every admin route change, focus moves to the new screen's `h1` (which has `tabindex="-1"`) and `document.title` changes to the title in `content.md`. Exception: errors move focus to the error notice or summary instead (UX-006). (2.4.3, 2.4.2) **[unit]** after each transition `document.activeElement` is the h1 and the title matches.
- **UX-004 Target size.** Customer controls (buttons, links styled as buttons, radios and checkbox rows, frame cards, the file chooser, text buttons such as **Change frame**) are at least 44 x 44 CSS px (`target-min`). Admin controls are at least 24 x 24 CSS px, row buttons in A2 at least 32 px high (`target-min-dense`), with at least 8 px between adjacent targets. Inline text links inside sentences are exempt. (2.5.8; 44 px is our stricter customer rule) **[manual]/[e2e]** measure bounding boxes at 390 px width.
- **UX-005 Labels and names.** Every form control has a visible `<label>` (or `<legend>` for radio groups) bound by `for`/`id`; placeholders are never the only label (we don't use placeholders); hints are linked with `aria-describedby`; every button and link has an accessible name that starts with its visible text (icon-only buttons have `aria-label`; we have none in the slice except the dialog **Close**, which shows the word "Close"). Units are in the label ("Inner width (mm)"). (1.3.1, 2.5.3, 3.3.2, 4.1.2) **[unit]** `getByLabelText` / `getByRole(name)` for every control listed in `screens.md`; **[axe]**.
- **UX-006 Form errors.** On a failed submit (browser check or API `validation_failed` / field codes): (a) an error summary with heading "There is a problem" appears at the top of the form, lists every error as a link that moves focus to its field, and receives focus; (b) each invalid field shows its message (from `content.md`) directly under its label, starting with a visually hidden "Error:" and an icon, in `color.danger`; (c) the field has `aria-invalid="true"` and `aria-describedby` that includes the error's id (before the hint id); (d) entered values are kept; (e) a field's error disappears when the field is corrected and loses focus. Single-field forms (A7, stock amount) and non-field errors (e.g. sold out, network) skip the summary and focus a notice with `role="alert"` instead. Validation never runs on every keystroke and never on first focus. (3.3.1, 3.3.3, 3.3.4 "checked", 1.3.1, 4.1.3) **[unit]** AC-014 inputs produce the three messages, summary focused, links focus fields, `aria-invalid`/`aria-describedby` set, values kept.
- **UX-007 Autocomplete and input types; accessible login.** Customer fields use `autocomplete` = `name`, `email`, `address-line1` (street), `postal-code`, `address-level2` (city), `country` (on the radio inputs, values `NL`/`BE`); email is `type="email"`; numeric admin fields use `inputmode="numeric"` / `"decimal"` with `type="text"` (no `type="number"`, so the scroll wheel can't change values and "49,95" is accepted). The login fields use `autocomplete="username"` / `"current-password"`; pasting and password managers work (no `onpaste` blocking, no custom keyboard); **Show password** reveals the password. No CAPTCHA or cognitive test. (1.3.5, 3.3.8) **[unit]** attributes present; paste into password works.
- **UX-011 Not by colour alone.** Status badges always show their label; the **Late** tag has an icon and the word "Late"; errors have an icon and text and invalid fields get a 2 px border (not only a colour change); the selected frame card has a check icon and a thicker border in addition to colour; links in text are underlined. (1.4.1) **[unit]** badge text present; **[manual]** greyscale screenshot check.
- **UX-012 Contrast from tokens only.** All colours, font sizes, spacing and radii come from `tokens.css`; `python3 docs/ux/check-contrast.py` passes (every pair >= 4.5:1 text, >= 3:1 UI/focus); no new colour pair is used without adding it to the script. (1.4.3, 1.4.11) **[CI]** the script; **[unit/lint]** grep for hex colours / `px` font sizes outside `tokens.css`; **[axe]** colour-contrast rule.
- **UX-013 Zoom, reflow, text spacing.** The viewport meta is `width=device-width, initial-scale=1` (no `maximum-scale`, no `user-scalable=no`); every screen works at 320 CSS px wide without horizontal page scrolling (admin tables turn into stacked rows below `bp.md`; nothing else may scroll sideways), at 200 % browser text size without clipped or overlapping text, and with WCAG text-spacing overrides (line height 1.5, letter 0.12em, word 0.16em, paragraph 2em). No fixed heights on text containers; sizes in `rem`. (1.4.4, 1.4.10, 1.4.12) **[manual/e2e]** screenshots at 320 px and 200 % zoom.
- **UX-014 Language and translation-ready text.** `<html lang="en">`; every string comes from the message catalogue with the keys in `content.md` (ICU placeholders, no concatenation); prices, dates and plurals are formatted with `Intl` as in `content.md` "Formatting". (3.1.1) **[unit]** a test renders with a pseudo-locale catalogue and finds no untranslated literal; formatter tests: 4995 -> "€49.95", "2026-11-17" -> "Tuesday 17 November 2026" in any client time zone.
- **UX-015 Page titles.** Each step and screen has the unique `document.title` from `content.md` (`c1.title` ... `a7.title`), updated on every step/route change and when the A2 filter changes. (2.4.2) **[unit]**.
- **UX-016 Landmarks, headings, skip link.** Each page has `header`, `main` and (shop) `footer` landmarks, the admin `nav` labelled "Admin"; exactly one `h1` per screen and section headings `h2` in order (no skipped levels); a "Skip to content" link is the first focusable element and moves focus to `main`. (1.3.1, 2.4.1, 2.4.6) **[axe]** landmark/heading rules; **[unit]** skip link target.
- **UX-021 Status messages.** Results of actions that don't move focus (status changed, SVG downloaded, saved, copied, delivery date changed, stock adjusted) are written into one polite live region (`role="status"`) that is in the DOM from page load; the same text is also visible on screen (success notice or updated row) and stays until the next action or navigation - nothing disappears on a timer, except the "Copied" button label (the region message stays). Load errors and action errors use `role="alert"` notices. (4.1.3, 2.2.1) **[unit]** after **Mark drawn** the status region contains "FL-2026-0042 is now Drawn."
- **UX-022 Busy and disabled buttons.** Submit buttons are never disabled to signal invalid input: they stay enabled and pressing them shows the errors (UX-006). While a request runs, the pressed button keeps its size, shows the busy label (`content.md`, e.g. "Placing order..."), gets `aria-disabled="true"` and ignores further presses, so an order can't be sent twice; it is restored on any outcome. (4.1.2, 3.3.4) **[unit]** double press of **Place order** sends one request; the button's name is "Placing order..." while pending.
- **UX-024 Dialogs.** Dialogs (X4 Log in again, X5 confirmations, C3 **View full size**) use `<dialog>` opened with `showModal()` (or an equivalent with `role="dialog"`, `aria-modal="true"`): labelled by their `h2` (`aria-labelledby`), described by their body text; on open focus goes to the safe choice (X5: **Keep order**/**Not yet**/**Keep going**; X4: Username; full size: **Close**); Tab stays inside; Escape closes it like the safe choice (X4: Escape closes the dialog and leaves the page as it was; the next admin call opens it again); on close focus returns to the control that opened it. The page behind is inert. (2.1.2, 2.4.3, 4.1.2) **[unit]** open/Escape/focus return for each dialog.
- **UX-026 Nothing entered is lost.** Going back a step, a sold-out frame (F6), an expired preview (F7), a network error, a rate limit or a re-login (X4) never clears what the customer or admin typed: name, email, address, terms tick and frame choice survive within the page session; after F7 the customer doesn't type their details again. (3.3.7) **[unit]** AC-020 flow: after `frame_sold_out`, C5 fields are still filled when the customer returns via C4.

## Customer flow

- **UX-008 Live region for the drawing progress.** C2 has a polite live region (`role="status"`, present in the DOM before the photo is sent) that announces, once each: "Sending your photo" at start, `c2.converting` when the upload finishes, `c2.slow` after 10 s; never the percentage on every tick (the `<progress>` element, labelled `c2.progressLabel`, exposes the value on demand). The `<progress>` is indeterminate (no `value`) while converting. The step's `main` has `aria-busy="true"` during conversion. Success is announced by the focus move to C3's h1 "Your drawing is ready"; errors by the focused `role="alert"` notice on C1. **Cancel** is reachable by keyboard throughout. (4.1.3, 2.2.2 not triggered - see UX-010) **[unit]** fake timers: region texts at 0 s, upload end, +10 s; focus on C3 h1 after success.
- **UX-009 Text alternatives.** The preview is an `<img>` (data URL, never inline SVG) with `alt="Preview of your line drawing, made from your photo"`; the C2 thumbnail `alt="Your photo"`; the C5 summary thumbnail `alt="Your drawing"`; frame photos in C4 and A4 thumbnails `alt=""` because the frame name is the adjacent text; the A3 drawing and photo and the A6 current photo use the alts in `content.md`; decorative illustrations and icons next to text have `alt=""` / `aria-hidden="true"`. (1.1.1) **[unit]** `getByRole("img", { name })` for each informative image; **[axe]** image-alt.
- **UX-010 Reduced motion.** With `prefers-reduced-motion: reduce`: no animation and no transition longer than 0 ms anywhere; the C2 pen animation is replaced by its static illustration; spinners are replaced by a static icon plus the busy text; step changes don't slide or fade. Without the preference, motion is limited to the pen animation (loops only while C2 is shown, which ends by success, error or the 45 s timeout), fades of at most 250 ms and spinners; nothing flashes more than 3 times per second. (2.3.1, 2.3.3 best effort, 2.2.2) **[unit]** with `matchMedia` mocked to reduce, the animated element isn't rendered; **[manual]** OS setting on a phone.
- **UX-017 Step indicator.** The step indicator is an ordered list labelled "Progress" with the visible text "Step {n} of 4: {name}"; the current item has `aria-current="step"`; completed steps have a check icon with visually hidden "completed"; it is not interactive. (1.3.1, 2.4.8 best effort) **[unit]**.
- **UX-018 Frame choice.** Frames are a native radio group in a `<fieldset>` with `<legend>` "Frame"; each card is the `<label>` of one radio (the whole card, at least 44 px, selects it); each radio's accessible name is "{name}, {width} x {height} mm, {price}"; arrow keys move between frames; no frame is preselected; the C4 required error is linked to the fieldset with `aria-describedby` and focus goes to the first radio. Sold-out frames are not rendered at all (no disabled radios). (1.3.1, 4.1.2, 3.3.1) **[unit]** AC-013: one radio named "Oak A4, 210 x 297 mm, €49.95", none for "Black A4".
- **UX-025 Time limits.** The only customer time limit is the preview's 24 h lifetime (longer than 20 hours, so it falls under the WCAG 2.2.1 exception); C3 shows when it ends (`c3.expiryNote`). The browser's 45 s wait after upload is not a user time limit (the customer can **Try again** at once). No session timeout or auto-advance anywhere in the customer flow. (2.2.1) **[unit]** expiry note from `expiresAt` in Europe/Amsterdam.
- **UX-028 File choosers.** **Choose a photo** (C1), **Photo** (A5) and **Choose a new photo** (A6) are native `<input type="file">` elements: if visually restyled, the input is visually hidden but stays focusable (not `display: none`), the styled `<label>` shows the focus ring via `:focus-within`, and the requirements text is linked with `aria-describedby`. Drag and drop is only ever an addition, never the only way. Pre-check errors use the same messages and focus behaviour as API errors. (2.1.1, 2.5.7, 3.3.2) **[unit]** `userEvent.upload` on the labelled input; keyboard focus reaches it.
- **UX-029 Consistent help.** The contact line (`shop.footer.contact`) appears in the same place (footer) on every customer step including C6 and X3. (3.2.6) **[unit]** footer present in each step render.
- **UX-030 Enlarge the preview.** Pinch-zoom is never blocked on the preview; **View full size** opens a dialog (UX-024) showing the drawing at full viewport width, scrollable in both directions, with **Close**. (1.4.4 supporting, low-vision use) **[unit]** dialog opens with the same image and alt.

## Admin tool

- **UX-019 Data tables.** A2 and A4 lists (from `bp.md`) are a `<table>` with a `<caption>` (filter, sort order and count, `content.md`), `<th scope="col">` headers, and the order number / frame name as a real link in its cell; below `bp.md` the stacked rows are a list (`<ul>`) where each item has the same content with visible labels ("Delivery date: Tue 17 Nov 2026"). The filter nav uses links with `aria-current="page"` on the active filter (not a tablist). (1.3.1, 1.3.2, 4.1.2) **[unit]** caption text, header cells, AC-029 row order; **[axe]**.
- **UX-020 Keyboard workflow for the day's drawings.** F11 can be completed with the keyboard only: from A2, Tab reaches each row's next-step button in row order; after a row action completes, focus stays on that row's (now updated) button, the row doesn't move or disappear until **Refresh list** or a filter change, and the result is announced (UX-021). No single-character keyboard shortcuts are added. (2.1.1, 2.1.4, 2.4.3, 3.2.2) **[unit]** download -> status cell "Drawing" -> focused button now "Mark drawn for FL-2026-0042".
- **UX-023 Session end without losing work.** An admin API call answering 401 opens the X4 **Log in again** dialog on top of the current page instead of navigating away; after a successful login the failed request is sent again once and focus returns to the control that started it; form contents are kept. Direct page loads without a session redirect to A1 with `next` (AC-026). The session timeout (8 h idle, design and Q-32) is much longer than a working session; with work preserved on re-login this is our answer to 2.2.1 for the admin. (2.2.1, 3.3.7) **[unit]** mocked 401 on **Save lead time** -> dialog -> login -> request retried, value kept.
- **UX-027 Names of repeated actions.** Repeated row buttons and links include the item they act on in their accessible name, after the visible text: "Download SVG for FL-2026-0042", "Mark drawn for FL-2026-0042" (visually hidden suffix `action.rowSuffix`); "Copy address" and A3 buttons need no suffix (one order per page). (2.4.4, 2.4.6, 2.5.3) **[unit]** `getByRole("button", { name: "Download SVG for FL-2026-0042" })`.
- **UX-031 Number and money fields.** Price fields accept "49.95", "49,95" and "€ 49.95" and send whole cents (4995); more than two decimals, zero or negative give `frame.error.price.invalid`. Whole-number fields (sizes, stock, stock amount, lead time) accept surrounding spaces and reject decimals with the field's message (AC-046: "2.5" -> `a7.error.leadTime`). The hint shows an example of the expected format. (3.3.1, 3.3.3) **[unit]** parse table tests.
- **UX-032 Confirm irreversible actions.** **Cancel order** and **Mark shipped** (both final, BR-009) open an X5 confirmation that names the order number and the consequence; nothing changes until the confirming button is pressed; the safe choice is focused first. Other forward steps (**Mark drawn**, **Mark ready to ship**, downloads) act at once to keep the daily flow fast. (3.3.4 "confirmed" for actions that can't be undone) **[unit]** cancel without confirming sends no request; AC-035 after confirming.

## Checklist per screen state (for the review)

For each state in `screens.md`: axe shows no violations; Tab order is logical and focus visible; the state's text matches `content.md`; at 320 px nothing scrolls sideways; with reduced motion nothing moves. Things only a person can confirm: a VoiceOver (iOS Safari) pass through F1 and F4, a TalkBack (Android Chrome) pass through F4 with an error, and a NVDA or VoiceOver (macOS) pass through F11 and F13.
