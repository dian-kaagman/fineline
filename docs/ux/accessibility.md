# Accessibility requirements - first slice

Target: **WCAG 2.2 level AA** for every screen in `screens.md`, on current phone browsers (iOS Safari, Android Chrome) and laptop browsers. Builders cite these IDs in test names (e.g. `it("UX-006 links each error to its field")`); the UX review checks them one by one.

## How each requirement is verified

| Tag | Where | What it can prove |
|---|---|---|
| **[jsdom]** | Vitest + Testing Library (+ `vitest-axe` for structural rules: names, roles, labels, landmarks, alt) in `apps/web`, during the build | DOM structure, ARIA, focus moves, keyboard events, texts, request counts. **Not** layout, sizes, colours, CSS, real focus rings or zoom: jsdom has no layout engine and no cascade (bounding boxes are 0, axe skips colour contrast). jsdom also has no `HTMLDialogElement.showModal`; stub it in tests |
| **[CI]** | a script or grep in CI | Token contrast (`python3 docs/ux/check-contrast.py`), no hard-coded colours/sizes, no `outline: none`, `lang` and viewport meta in `index.html` |
| **[browser]** | the post-build UX review: the built app in Chromium (Playwright screenshots at 390 x 844 and 1280 x 800, `@axe-core/playwright` on each reachable state) plus keyboard, zoom and screen-reader checks by a person | Target sizes, contrast as rendered, focus visibility, reflow at 320 px and 200 %, reduced motion, pinch-zoom, real dialog behaviour |

The index says which applies; a requirement with both tags needs both.

## General (customer and admin)

- **UX-001 Keyboard operable.** Every interactive element can be reached with Tab / Shift+Tab and operated with Enter or Space (radios and the frame choice with the arrow keys); there is no keyboard trap except inside an open modal dialog (UX-024); the Tab order follows the visual order top-to-bottom, left-to-right. Only native interactive elements (`button`, `a[href]`, `input`, `select`, `summary`) or elements with the matching ARIA role and key handling; no click handlers on `div`/`tr`. (2.1.1, 2.1.2, 2.4.3) **[jsdom]** each action fired via `userEvent.keyboard`/`userEvent.tab`; **[browser]** tab through each screen.
- **UX-002 Focus visible and not hidden.** Every focusable element shows the focus ring from the tokens (`:focus-visible`, 3 px `color.focus`, 2 px offset, at least 3:1 against the background, see `design-tokens.md`); `outline: none` is never used without this replacement; a focused element is never fully covered by the sticky admin header or any other content (`scroll-padding-top: header-height + space.4`). (2.4.7, 2.4.11, 1.4.11) **[CI]** grep finds no `outline: none`/`outline: 0` outside `tokens.css`; **[browser]** tab through at 1280 px and 390 px.
- **UX-003 Focus and title after navigation.** After every customer step change (C1->C2->C3->C4->C5->C6, and back) and every admin route change, focus moves to the new screen's `h1` (which has `tabindex="-1"`) and `document.title` changes to the title in `content.md`. Exception: errors move focus to the error notice or summary instead (UX-006). (2.4.3, 2.4.2) **[jsdom]** after each transition `document.activeElement` is the h1 and the title matches.
- **UX-004 Target size.** Customer controls (buttons, links styled as buttons, radios and checkbox rows, frame cards, the file chooser, text buttons such as **Change frame**) are at least 44 x 44 CSS px (`target-min`). Admin controls are at least 24 x 24 CSS px, row buttons in A2 at least 32 px high (`target-min-dense`), with at least 8 px between adjacent targets. Inline text links inside sentences are exempt. (2.5.8; 44 px is our stricter customer rule) **[browser]** bounding boxes measured at 390 px wide in the post-build review (jsdom has no layout, so no unit test can check this).
- **UX-005 Labels and names.** Every form control has a visible `<label>` (or `<legend>` for radio groups) bound by `for`/`id`; placeholders are never the only label (we don't use placeholders); hints are linked with `aria-describedby`; every button and link has an accessible name that starts with its visible text (no icon-only buttons in the slice). Units are in the label ("Inner width (mm)"). (1.3.1, 2.5.3, 3.3.2, 4.1.2) **[jsdom]** `getByLabelText` / `getByRole(name)` for every control listed in `screens.md`; `vitest-axe` label rules.
- **UX-006 Form errors.** On a failed submit (browser check or API `validation_failed` with `details`, or a field code such as `country_not_supported`, `photo_terms_not_accepted`, `delivery_date_before_order_date`): (a) an error summary with heading "There is a problem" appears at the top of the form, lists every error as a link that moves focus to its field, and receives focus; (b) each invalid field shows its message (from `content.md`) directly under its label, starting with a visually hidden "Error:" and an icon, in `color.danger`; (c) the field has `aria-invalid="true"` and `aria-describedby` that includes the error's id (before the hint id); (d) entered values are kept; (e) a field's error disappears when the field is corrected and loses focus. Single-field forms (A7, stock amount, delivery date) and non-field errors (e.g. sold out, network) skip the summary and focus a notice with `role="alert"` instead. Validation never runs on every keystroke and never on first focus. (3.3.1, 3.3.3, 3.3.4 "checked", 1.3.1, 4.1.3) **[jsdom]** AC-014 inputs produce the three messages, summary focused, links focus fields, `aria-invalid`/`aria-describedby` set, values kept; AC-041 API `details` for `priceCents`, `stock`, `photo` shown on their fields.
- **UX-007 Autocomplete and input types; accessible login.** Customer fields use `autocomplete` = `name`, `email`, `address-line1` (street), `postal-code`, `address-level2` (city), `country` (on the radio inputs, values `NL`/`BE`); email is `type="email"`; numeric admin fields use `inputmode="numeric"` / `"decimal"` with `type="text"` (no `type="number"`, so the scroll wheel can't change values and "49,95" is accepted). The login fields use `autocomplete="username"` / `"current-password"`; pasting and password managers work (no `onpaste` blocking, no custom keyboard); **Show password** reveals the password. No CAPTCHA or cognitive test. (1.3.5, 3.3.8) **[jsdom]** attributes present; paste into password works.
- **UX-011 Not by colour alone.** Status badges always show their label; errors have an icon and text and invalid fields get a 2 px border (not only a colour change); the selected frame card has a check icon and a thicker border in addition to colour; links in text are underlined. (1.4.1) **[jsdom]** badge text and check icon present; **[browser]** greyscale screenshot check.
- **UX-012 Contrast from tokens only.** All colours, font sizes, spacing and radii come from `tokens.css`; `python3 docs/ux/check-contrast.py` passes (every pair >= 4.5:1 text, >= 3:1 UI/focus); no new colour pair is used without adding it to the script. (1.4.3, 1.4.11) **[CI]** the script, and a grep for hex/rgb colours and `px` font sizes outside `tokens.css`; **[browser]** axe colour-contrast on the rendered pages (axe can't check contrast in jsdom).
- **UX-013 Zoom, reflow, text spacing.** The viewport meta is `width=device-width, initial-scale=1` (no `maximum-scale`, no `user-scalable=no`); every screen works at 320 CSS px wide without horizontal page scrolling, at 200 % browser text size without clipped or overlapping text, and with WCAG text-spacing overrides (line height 1.5, letter 0.12em, word 0.16em, paragraph 2em). The only thing that may scroll sideways is an admin data table (A2, A4), inside its own focusable, labelled scroll region (`role="region"`, `tabindex="0"`, `aria-labelledby` the caption) - data tables are an allowed exception of 1.4.10. No fixed heights on text containers; sizes in `rem`. (1.4.4, 1.4.10, 1.4.12) **[CI]** viewport meta in `index.html`; **[browser]** screenshots at 320 px and 200 % zoom.
- **UX-014 Language and translation-ready text.** `<html lang="en">`; every string comes from one flat key -> string catalogue with the keys in `content.md` (named `{placeholders}` filled by simple replacement, `.one`/`.other` keys where a count changes the words, no sentences glued from pieces); prices and dates are formatted with `Intl` as in `content.md` "Formatting". (3.1.1) **[CI]** `lang="en"` in `index.html`; **[jsdom]** formatter tests: 4995 -> "€49.95", "2026-11-17" -> "Tuesday 17 November 2026" with the test process in a time zone west of UTC (e.g. `TZ=America/New_York`), and every key used in components exists in the catalogue.
- **UX-015 Page titles.** Each step and screen has the unique `document.title` from `content.md` (`c1.title` ... `a7.title`), updated on every step/route change and when the A2 filter changes. (2.4.2) **[jsdom]**.
- **UX-016 Landmarks, headings, skip link.** Each page has `header`, `main` and (shop) `footer` landmarks, the admin `nav` labelled "Admin"; exactly one `h1` per screen and section headings `h2` in order (no skipped levels); a "Skip to content" link is the first focusable element and moves focus to `main`. (1.3.1, 2.4.1, 2.4.6) **[jsdom]** `vitest-axe` landmark/heading rules, skip link target.
- **UX-021 Status messages.** Results of actions that don't move focus (status changed, SVG downloaded, saved, delivery date changed, stock adjusted) are written into one polite live region (`role="status"`) that is in the DOM from page load; the same text is also visible on screen (success notice or updated row) and stays until the next action or navigation - nothing disappears on a timer. Load errors and action errors use `role="alert"` notices. (4.1.3, 2.2.1) **[jsdom]** after **Mark drawn** the status region contains "FL-2026-0042 is now Drawn."
- **UX-022 Busy and disabled buttons.** Submit buttons are never disabled to signal invalid input: they stay enabled and pressing them shows the errors (UX-006). While a request runs, the pressed button keeps its size, shows the busy label (`content.md`, e.g. "Placing order..."), gets `aria-disabled="true"` and ignores further presses, so an order can't be sent twice; it is restored on any outcome. (4.1.2, 3.3.4) **[jsdom]** double press of **Place order** sends one request; the button's name is "Placing order..." while pending.
- **UX-024 Dialogs.** The X5 confirmation dialogs (cancel order, mark shipped, start again) use `<dialog>` opened with `showModal()` (or an equivalent with `role="dialog"`, `aria-modal="true"`): labelled by their `h2` (`aria-labelledby`), described by their body text; on open focus goes to the safe choice (**Keep order** / **Not yet** / **Keep going**); Tab stays inside; Escape closes it like the safe choice; on close focus returns to the control that opened it. The page behind is inert. (2.1.2, 2.4.3, 4.1.2) **[jsdom]** with `showModal` stubbed: names, initial focus, Escape, focus return; **[browser]** real focus containment and inertness.
- **UX-026 Nothing entered is lost.** Going back a step, a sold-out frame (F6), a preview that is no longer available (F7), a network error or a rate limit never clears what the customer or admin typed: name, email, address, terms tick and frame choice stay in memory for as long as the page is open; after F7 the customer doesn't type their details again. A reload or an ended admin session (UX-023) does lose unsaved input - accepted for this slice. (3.3.7) **[jsdom]** AC-020 flow: after `frame_sold_out`, C5 fields are still filled when the customer returns via C4.

## Customer flow

- **UX-008 Live region for the drawing progress.** C2 has a polite live region (`role="status"`, present in the DOM before the photo is sent) that announces `c2.working` ("Making your drawing. This usually takes a few seconds.") **once**, when the request starts. The `<progress>` is indeterminate (no `value`) and labelled `c2.progressLabel`. The step's `main` has `aria-busy="true"` while the request runs. Success is announced by the focus move to C3's h1 "Your drawing is ready"; errors by the focused `role="alert"` notice on C1. **Cancel** is reachable by keyboard throughout. (4.1.3, AC-007) **[jsdom]** the region holds `c2.working` exactly once while the request is pending; focus on C3 h1 after success; **Cancel** aborts the request.
- **UX-009 Text alternatives.** The preview is an `<img>` whose `src` is a `data:image/svg+xml` URL of the returned SVG (never inline SVG, AC-056) with `alt="Preview of your line drawing, made from your photo"`; the A3 drawing is shown the same way with `alt="Drawing for order {orderNumber}"`; the C2 thumbnail `alt="Your photo"`; the C5 summary thumbnail `alt="Your drawing"`; frame photos in C4 and A4 thumbnails `alt=""` because the frame name is the adjacent text; the A3 photo and the A6 current photo use the alts in `content.md`; decorative illustrations and icons next to text have `alt=""` / `aria-hidden="true"`. (1.1.1) **[jsdom]** `getByRole("img", { name })` for each informative image, its `src` starts with `data:image/svg+xml`, and the drawing's markup is not in the document (no `path` element with the drawing's `d` data); `vitest-axe` image-alt.
- **UX-010 Reduced motion.** With `prefers-reduced-motion: reduce`: no animation and no transition longer than 0 ms anywhere; the C2 pen animation is replaced by its static illustration; spinners are replaced by a static icon plus the busy text; step changes don't slide or fade. Without the preference, motion is limited to the pen animation (loops only while C2 is shown, which ends by success, error or **Cancel**), fades of at most 250 ms and spinners; nothing flashes more than 3 times per second. (2.3.1, 2.3.3 best effort, 2.2.2) **[jsdom]** with `matchMedia` mocked to reduce, the animated element isn't rendered; **[browser]** emulated `prefers-reduced-motion` and the OS setting on a phone.
- **UX-017 Step indicator.** The step indicator is an ordered list labelled "Progress" with the visible text "Step {n} of 4: {name}"; the current item has `aria-current="step"`; completed steps have a check icon with visually hidden "completed"; it is not interactive. (1.3.1, 2.4.8 best effort) **[jsdom]**.
- **UX-018 Frame choice.** Frames are a native radio group in a `<fieldset>` with `<legend>` "Frame"; each card is the `<label>` of one radio (the whole card, at least 44 px, selects it); each radio's accessible name is "{name}, {width} x {height} mm, {price}"; arrow keys move between frames; no frame is preselected; the C4 required error is linked to the fieldset with `aria-describedby` and focus goes to the first radio. Sold-out frames are not rendered at all (no disabled radios). (1.3.1, 4.1.2, 3.3.1) **[jsdom]** AC-013: one radio named "Oak A4, 210 x 297 mm, €49.95", none for "Black A4".
- **UX-025 Time limits.** The only customer time limit is the preview's 24 h lifetime (longer than 20 hours, so it falls under the WCAG 2.2.1 exception); C3 shows when it ends (`c3.expiryNote`). The web app sets no timeout of its own on the drawing request. No session timeout or auto-advance anywhere in the customer flow. (2.2.1) **[jsdom]** expiry note from `expiresAt` in Europe/Amsterdam.
- **UX-028 File choosers.** **Choose a photo** (C1), **Photo** (A5) and **Choose a new photo** (A6) are native `<input type="file">` elements: if visually restyled, the input is visually hidden but stays focusable (not `display: none`), the styled `<label>` shows the focus ring via `:focus-within`, and the requirements text is linked with `aria-describedby`. There is no drag and drop in this slice, so nothing depends on a dragging movement. Pre-check errors use the same messages and focus behaviour as API errors. (2.1.1, 2.5.7, 3.3.2) **[jsdom]** `userEvent.upload` on the labelled input; keyboard focus reaches it; **[browser]** the focus ring is visible on the styled label.
- **UX-029 Consistent help.** The contact line (`shop.footer.contact`, address from `VITE_CONTACT_EMAIL`) appears in the same place (footer) on every customer step including C6 and X3. (3.2.6) **[jsdom]** footer present in each step render.
- **UX-030 Zoomable preview.** The preview can be enlarged: pinch-zoom and browser zoom are never blocked (viewport meta as in UX-013; no `touch-action: none` or gesture handlers on the preview or its ancestors; no overlay covers it); the `<img>` scales with its container (`width: 100%; height: auto`, no fixed pixel size), so at 200 % zoom it gets larger and stays sharp (SVG). There is no "View full size" dialog in this slice. (1.4.4 supporting, low-vision use) **[CI]** viewport meta; **[browser]** pinch-zoom on a phone (or emulated) and 200 % browser zoom show the drawing larger and sharp.

## Admin tool

- **UX-019 Data tables.** A2 and A4 lists are a `<table>` at every width, with a `<caption>` (filter, sort order and count, `content.md`), `<th scope="col">` headers, and the order number / frame name as a real link in its cell; on narrow screens the table scrolls inside its region (UX-013) - there is no stacked-row variant. The A2 filter nav uses links with `aria-current="page"` on the active filter (not a tablist). (1.3.1, 1.3.2, 4.1.2) **[jsdom]** caption text, header cells, AC-029 row order; `vitest-axe` table rules.
- **UX-020 Keyboard workflow for the day's drawings.** F11 can be completed with the keyboard only: from A2, Tab reaches each row's next-step button in row order; after a row action completes, focus stays on that row's (now updated) button, the row doesn't move or disappear until **Refresh list** or a filter change, and the result is announced (UX-021). No single-character keyboard shortcuts are added. (2.1.1, 2.1.4, 2.4.3, 3.2.2) **[jsdom]** **Download SVG** -> one `POST .../drawing-download` -> status cell "Drawing" -> focused button now "Mark drawn for FL-2026-0042".
- **UX-023 Session end.** When an admin API call answers 401 (no session, idle for 8 h or older than 24 h, AC-063), the web app navigates to `/admin/login?next=<current path>` and A1 shows `a1.sessionEnded` ("Your session has ended. Log in again to continue."); after logging in it returns to that path (same-origin `/admin/...` paths only). Opening an admin page without a session does the same (AC-026). Unsaved input on the page is lost; the 8-hour idle limit is far longer than a working session, so this is accepted for the slice (a re-login dialog that keeps the work is "Later"). (2.2.1, 3.3.7 partly) **[jsdom]** mocked 401 on **Save lead time** -> location is `/admin/login?next=%2Fadmin%2Fsettings` and the notice is shown; after a mocked login the settings page is shown again; `next=https://evil.example` is ignored.
- **UX-027 Names of repeated actions.** Repeated row buttons and links include the item they act on in their accessible name, after the visible text: "Download SVG for FL-2026-0042", "Mark drawn for FL-2026-0042" (visually hidden suffix `action.rowSuffix`); A3 buttons need no suffix (one order per page). (2.4.4, 2.4.6, 2.5.3) **[jsdom]** `getByRole("button", { name: "Download SVG for FL-2026-0042" })`.
- **UX-031 Number and money fields.** Price fields accept "49.95", "49,95" and "€ 49.95" and send whole cents (4995); more than two decimals, zero or negative give `frame.error.price.invalid`. Whole-number fields (sizes, stock, stock amount, lead time) accept surrounding spaces and reject decimals with the field's message (AC-046: "2.5" -> `a7.error.leadTime`). The hint shows an example of the expected format. (3.3.1, 3.3.3) **[jsdom]** parse table tests.
- **UX-032 Confirm irreversible actions.** **Cancel order** and **Mark shipped** (both final, BR-009) open an X5 confirmation that names the order number and the consequence; nothing changes until the confirming button is pressed; the safe choice is focused first. Other forward steps (**Mark drawn**, **Mark ready to ship**, downloads) act at once to keep the daily flow fast. (3.3.4 "confirmed" for actions that can't be undone) **[jsdom]** cancel without confirming sends no request; AC-035 after confirming.

## Checklist per screen state (post-build browser review)

For each state in `screens.md`: axe in a real browser shows no violations; Tab order is logical and focus visible; the state's text matches `content.md`; at 320 px nothing but an admin table region scrolls sideways; targets measure at least 44 px (customer) / 24 px (admin); with reduced motion nothing moves. Things only a person can confirm: a VoiceOver (iOS Safari) pass through F1 and F4, a TalkBack (Android Chrome) pass through F4 with an error, and a NVDA or VoiceOver (macOS) pass through F11 and F13.
